# Git 提交备注规范

本文约定 Minifeel 仓库的 Commit Message 写法，便于阅读历史、生成变更说明，以及按类型筛选改动。

采用 [Conventional Commits](https://www.conventionalcommits.org/) 风格；说明文字可使用中文。

## 格式

```text
<类型>(可选范围): <简短说明>

[可选正文]

[可选脚注]
```

- **类型（type）**：必填，见下表。
- **范围（scope）**：可选，标明模块。
- **简短说明**：必填，一句话说清「做了什么」。
- **正文**：可选，说明「为什么改」、影响面、迁移注意点。
- **脚注**：可选，如 `BREAKING CHANGE:`、关联 Issue（`Closes #123`）。

## 类型

| 类型 | 含义 | 示例场景 |
| --- | --- | --- |
| `feat` | 新功能 | 画布支持批量重命名 |
| `fix` | 修复缺陷 | 协议安装超时 |
| `docs` | 仅文档 | README、开发指南、注释性说明文档 |
| `style` | 代码格式 | 空格、分号、排版，不改变逻辑 |
| `refactor` | 重构 | 拆分模块、重命名，非功能/非修 Bug |
| `perf` | 性能优化 | 减少渲染、加快接口 |
| `test` | 测试 | 新增或调整测试用例 |
| `build` | 构建与依赖 | Bun、打包脚本、依赖版本 |
| `ci` | 持续集成 | GitHub Actions、发布流水线 |
| `chore` | 杂项 | 工具脚本、不影响业务逻辑的维护 |
| `revert` | 回滚 | 撤销某次提交 |

## 范围（建议）

按改动所在模块填写，常见取值：

| 范围 | 对应区域 |
| --- | --- |
| `web` | `apps/web` |
| `server` | `apps/server` |
| `desktop` | `apps/desktop` |
| `canvas` | 画布相关 |
| `agent` | Agent 运行时 |
| `mcp` | MCP 相关 |
| `node` | 节点插件 |
| `tool` | 工具插件 |
| `docs` | 文档目录 |

范围可省略；跨多个模块且不好归类时可不写。

## 说明怎么写

1. 使用祈使、现在时：`添加`、`修复`、`调整`，避免 `添加了`、`修复了`。
2. 首行尽量控制在 **50 个汉字以内**（或约 72 个英文字符）。
3. 首行只写「做了什么」；「为什么」放正文。
4. **一条提交只做一件事**；大改请拆分。
5. 不要在提交信息中写入密钥、Token、密码或个人隐私路径。

## 示例

```text
feat(canvas): 支持节点批量重命名
```

```text
fix(desktop): 修复 minifeel:// 协议安装超时
```

```text
docs: 补充 Windows 本地启动说明
```

```text
refactor(server): 拆分 agent session 加载逻辑

原 sessions.ts 过长，拆出独立模块便于维护。
```

```text
feat(web)!: 设置页改用新配置结构

BREAKING CHANGE: 旧版 settings.json 需手动迁移一次。
```

```text
chore: 更新 bun 依赖版本
```

```text
ci: 调整桌面端发布工作流触发条件
```

类型后加 `!`，或脚注写 `BREAKING CHANGE:`，表示不兼容变更。

## 不建议的写法

```text
update
修改代码
fix bug
临时提交
WIP
asdf
```

含义不清、无法检索，也不利于生成发布说明。

## 与分支的配合（建议）

| 分支 | 用途 |
| --- | --- |
| `main` | 稳定可发布 |
| `dev` | 日常开发集成 |
| `feat/<简述>` | 功能开发 |
| `fix/<简述>` | 缺陷修复 |

功能与修复建议先在对应分支提交，再合并到 `dev`；发布相关流程见 [开发与扩展指南](./development.md)。

## 检查清单

提交前自问：

- [ ] 类型是否选对（`feat` / `fix` / `docs` 等）？
- [ ] 首行能否让别人 3 秒内看懂改动？
- [ ] 是否混进了无关文件或调试代码？
- [ ] 是否误提交了密钥、`.env`、本地配置？
